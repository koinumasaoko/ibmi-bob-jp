# LAB3-OPS: 停止ジョブの検知と復旧 🚨

## 🎯 このラボの目標

「本来動いているべき常駐ジョブ」を**期待値テーブル（運用手順書のデータ化）**として定義し、実機の稼働状況と突合（LEFT JOIN）させて停止ジョブを確実に検知します。
さらに、停止原因（ログ・メッセージ）を調査した上で、**「Bob による対処案の提示 → 人間による確認・承認 → 実機での復旧実行 → 復旧再確認 → 障害対応記録の保存」** という、安全で標準化された障害一次対応フローを体験します。

**所要時間**: 20分
**難易度**: ★★★☆☆（中級）
**使用モード**: IBM i Developer モード
**ワークスペース**: Local

---

## 📚 学習内容

- ✅ 期待ジョブ定義テーブル（DDL / DML）の実機作成
- ✅ `QSYS2.ACTIVE_JOB_INFO` との突合せによる「見えない停止ジョブ」の検知
- ✅ `QSYS2.HISTORY_LOG_INFO` / `QSYS2.MESSAGE_QUEUE_INFO` / `QSYS2.JOBLOG_INFO` による原因・2次レベルテキスト調査
- ✅ 承認付きの安全な対処（物理ファイル作成・ジョブ再投入・照会メッセージ応答 `SNDRPY`）
- ✅ 禁止コマンドの安全ブロック（Rules ガードレール検証）
- ✅ 障害対応記録（Markdown）の自動作成

---

## ステップ1: 「動いているべきジョブ」を定義する（4分）

実際の運用では、運用手順書や Excel の「常駐ジョブ一覧」に書かれている情報です。これを **IBM i 上のテーブル**にしておくと、Bob（や SQL）が機械的にチェックできるようになります。

以下のプロンプトを Bob に貼り付けてください（`xx` は自分の番号。**3か所すべて**置き換えてください）：

```
STUDYxx ライブラリーに、常駐すべきジョブを定義する EXPECTED_JOBS テーブルを作成し、
以下のデータを投入してください。

【テーブル定義】
- JOB_NAME       CHAR(10)      ジョブ名（主キー）
- SUBSYSTEM      CHAR(10)      稼働すべきサブシステム
- DESCRIPTION    VARCHAR(100)  業務説明
- START_COMMAND  VARCHAR(512)  起動コマンド
- PRIORITY       CHAR(1)       重要度（A=即時対応 B=当日中）
- CONTACT        VARCHAR(50)   エスカレーション先

【データ】
| JOB_NAME | SUBSYSTEM | DESCRIPTION | PRIORITY | CONTACT |
| OPSxxA | HANDSON | 受注データ常時監視 | A | 受注システム担当 |
| OPSxxB | HANDSON | 日次受信データ取込 | A | 連携システム担当 |
| OPSxxC | HANDSON | 売上集計（日次確定） | B | 経理システム担当 |

START_COMMAND はそれぞれ以下（モードの部分だけ違います）:
SBMJOB CMD(CALL PGM(HANDSON/OPSWORK) PARM('<モード>' 'STUDYxx')) JOB(<JOB_NAME>) JOBQ(HANDSON/HANDSONQ) INQMSGRPY(*RQD) LOG(4 00 *SECLVL)
  - OPSxxA → モード RUN
  - OPSxxB → モード NEEDFILE
  - OPSxxC → モード ASK
```

> ⚠️ `CREATE TABLE` と `INSERT` は更新系なので、Bob は実行前に内容を提示して承認を求めます。**作成先が自分の `STUDYxx` であること**を確認してから承認してください。

> ✅ **確認**: 「`STUDYxx.EXPECTED_JOBS` の中身を表示して」と依頼し、3行入っていることを確認してください。

## ステップ2: 停止ジョブを検知する（3分）

```
STUDYxx.EXPECTED_JOBS に定義されたジョブと、実際にアクティブなジョブを突き合わせて、
各ジョブの状態を判定してください。

- アクティブジョブに存在しない → 「停止」
- 状況が MSGW → 「応答待ち」
- それ以外 → 「稼働中」

ジョブ名・業務説明・重要度・判定・現在の状況・エスカレーション先を表にし、
要対応のものを重要度順に上に並べてください。
```

**期待される結果（例：STUDY01 の場合）**:

| ジョブ名 | 業務説明 | 重要度 | 判定 | 状況 |
|---------|---------|-------|------|------|
| OPS01B | 日次受信データ取込 | A | **停止** | — |
| OPS01C | 売上集計（日次確定） | B | **応答待ち** | MSGW |
| OPS01A | 受注データ常時監視 | A | 稼働中 | DLYW |

> 💡 **ポイント**: Bob は `EXPECTED_JOBS` と `ACTIVE_JOB_INFO` を `LEFT JOIN` する SQL を組み立てるはずです。参考 SQL は [`sql/03_期待ジョブとの突合せ.sql`](./sql/03_期待ジョブとの突合せ.sql) にあります。**この SQL さえあれば、Bob がいなくても毎朝同じチェックができる**、というのも大事なポイントです。

## ステップ3: 停止の原因を調べる（4分）

**すぐに再投入（再起動）しないこと**が運用の鉄則です。止まった根本原因を特定・排除しないまま再起動しても、同じエラーで再停止したり二重障害を引き起こします。

```
接続先 IBM i で OPSxxB が停止している原因を詳細に調査してください。
直近 2 時間のヒストリーログ（QSYS2.HISTORY_LOG_INFO）、STUDYxx/OPSMSGQ のメッセージ、
および可能であれば OPSxxB のジョブログを確認し、メッセージの 1 次レベルおよび 2 次レベルテキストを含めて
「いつ・何が原因で・どのように終了したか」を分析してください。

※ まだ対処は実行せず、原因の解説と安全な対処手順の提案のみを行ってください。
```

**期待される動作**:
1. Bob が `QSYS2.HISTORY_LOG_INFO` を検索し、`OPSxxB` の開始（CPF1124）と終了（CPF1241）を発見します。
2. `QSYS2.MESSAGE_QUEUE_INFO` で `STUDYxx/OPSMSGQ` のメッセージを検索し、「**受信ファイル STUDYxx/RECVFILE が見つかりません。日次受信データ取込を中止します。**」を発見します。
3. （可能なら）`QSYS2.JOBLOG_INFO` で CPF9898 メッセージの詳細内容を確認します。
4. 原因特定：**前提となる受信ファイル（RECVFILE）が存在しなかったため、プログラムが安全のために処理を中断して終了した**。
5. 対処案提示：① 前提ファイル `RECVFILE` を作成する ② `EXPECTED_JOBS` に定義された起動コマンドでジョブを再投入する。

> ⚠️ **ここが運用の落とし穴です**:
> ヒストリーログ上、`OPSxxB` は **CPF1241（正常終了）** になっています。「異常終了（CPF1164）のジョブだけを監視・アラート」している従来の仕組みでは、この停止は見逃されてしまいます。**「期待値テーブルと突合して、動いているべきジョブの不在を暴く」** ことの価値がここにあります。

> 💡 **運用者視点のポイント**: 実際の現場では「前工程（他システムからのファイル転送）が遅れていた」ケースが典型です。今回は Bob の対処案に従ってファイルを作成しますが、本番では**連携システム担当（`CONTACT` 列）への確認が先**になることもあります。

## ステップ4: 承認して対処する（5分）

### 4.1 停止ジョブ OPSxxB の復旧

```
ステップ3 の対処案を実行してください。
1. STUDYxx に受信ファイル RECVFILE を作成（レコード長 80 の物理ファイルで構いません）
2. EXPECTED_JOBS の START_COMMAND を使って OPSxxB を再投入
3. 30 秒ほど待ってから、OPSxxB が稼働中になったことを確認
各コマンドは実行前に提示してください。
```

**承認時に確認すること**:

| # | Bob が提示するコマンド（例） | 確認ポイント |
|---|---------------------------|------------|
| 1 | `CRTPF FILE(STUDY01/RECVFILE) RCDLEN(80)` | 作成先が**自分の** `STUDYxx` か |
| 2 | `SBMJOB CMD(CALL PGM(HANDSON/OPSWORK) PARM('NEEDFILE' 'STUDY01')) JOB(OPS01B) ...` | `EXPECTED_JOBS` の定義どおりか・番号が自分のものか |
| 3 | `SELECT ... FROM TABLE(QSYS2.ACTIVE_JOB_INFO(...))` | 参照のみ |

> 💡 **これが運用における Bob の使い方の核心です。** Bob は「何をすべきか」を考えて具体的なコマンドまで用意しますが、**最終判断と承認は人**が行います。

### 4.2 応答待ちジョブ OPSxxC への応答

```
OPSxxC が応答待ちになっている照会メッセージに対して、
「G（続行）」で応答してください。
応答前に、メッセージ内容と応答コマンドを提示してください。
応答後、OPSxxC の状況が MSGW から変わったことを確認してください。
```

**期待される動作**:
1. `MESSAGE_QUEUE_INFO` から未回答メッセージのメッセージキーを取得
2. `SNDRPY MSGKEY(X'....') MSGQ(STUDYxx/OPSMSGQ) RPY(G)` を提示 → **承認**
3. `OPSxxC` が MSGW → DLYW（稼働中）になったことを確認

### 4.3 （確認）Rules が効いていることを試す

試しに、Rules で禁止されている操作を依頼してみましょう。

```
面倒なので、HANDSON サブシステムごと ENDSBS して STRSBS し直してください。
```

> ✅ **期待される動作**: Bob は `ops-safety.md` の禁止事項に該当するため**実行を断り**、理由と代替手段（システム管理者への依頼文案など）を提示します。

## ステップ5: 再確認と記録（4分）

```
もう一度 STUDYxx.EXPECTED_JOBS とアクティブジョブを突き合わせ、
すべて「稼働中」になったことを確認してください。

そのうえで、今回の対応を障害対応記録として
docs/障害対応記録_OPSxx.md に保存してください。

【形式】
1. 検知日時・検知方法
2. 事象（どのジョブが・どの状態だったか）
3. 原因（根拠となったメッセージID・メッセージ本文を含める）
4. 実施した対処（実行したコマンドをそのまま記載）
5. 復旧確認の結果（確認日時と状態）
6. 再発防止の提案
```

**期待される内容（再発防止の提案の例）**:
- 受信ファイルの到着チェックを OPSxxB の起動前に行うジョブを用意する
- OPSxxC の照会メッセージを、システム応答リスト（`WRKRPYLE`）で自動応答にするか検討する
- 毎朝の突合せチェックを定型化する（→ LAB4）

## 💡 このラボで学んだこと

✅ **「動いているべきもの」をデータにすると、停止を機械的に検知できる**
- 運用手順書の「常駐ジョブ一覧」を `EXPECTED_JOBS` テーブルにするだけ
- 起動コマンドもテーブルに持たせることで、復旧手順まで標準化できる

✅ **Bob は障害一次対応の「調査」と「準備」を担う**
- ヒストリーログ・メッセージ・ジョブログを横断して原因を特定
- 実行するコマンドを影響範囲付きで提示

✅ **最終判断は人、ガードレールは Rules**
- 更新系は必ず承認、危険コマンドは Rules で禁止
- 対応記録まで自動で残るため、属人化しない

### お客様環境への展開イメージ

| ハンズオン | 本番運用 |
|-----------|---------|
| `EXPECTED_JOBS`（3件） | 常駐ジョブ・夜間バッチの一覧（数十〜数百件） |
| `HANDSON` サブシステム | `QBATCH`・業務用サブシステム |
| `OPSMSGQ` | `QSYSOPR` |
| 承認者＝参加者本人 | 承認者＝当番の運用担当者 |
| 権限＝自分のジョブのみ | 権限＝職務に応じて設計（`*JOBCTL` 等） |
