# LAB2-OPS: ジョブ／サブシステムの見える化 🖥️

## 🎯 このラボの目標

5250 画面で `WRKSBS`・`WRKACTJOB`・`WRKJOBSCDE`・`DSPMSG QSYSOPR` を順番に開いて目視確認していた**日次の稼働確認作業**を、PP4i 接続の Bob に自然言語で一括依頼します。
実機の障害兆候（MSGW や保留ジョブ）を検知し、結果を**稼働状況レポート（HTML）**として出力する流れを体験します。

このラボは**参照系中心**です（ステップ0 の初期ジョブ投入を除く）。

**所要時間**: 15分
**難易度**: ★★☆☆☆（初中級）
**使用モード**: IBM i Developer モード
**ワークスペース**: Local

---

## 📚 学習内容

- ✅ `QSYS2.SUBSYSTEM_INFO` によるサブシステム一覧と状態確認
- ✅ `QSYS2.ACTIVE_JOB_INFO` によるアクティブジョブの高速絞り込み（実機負荷への配慮）
- ✅ 応答待ち（MSGW）ジョブと `QSYS2.MESSAGE_QUEUE_INFO` による未回答メッセージの検知
- ✅ `QSYS2.SCHEDULED_JOB_INFO` によるスケジュール項目の保留チェック
- ✅ 稼働状況レポート（HTML）の自動生成

---

## ステップ0: ハンズオン用ジョブを実機に投入する（1分）

接続先 IBM i 上のセットアッププログラムを呼び出し、自分専用の**模擬業務ジョブ**をサブシステム `HANDSON` に投入します。

```
接続先 IBM i で次の CL コマンドを実行してください（xx は 01 のように自分の番号）：
CALL PGM(HANDSON/OPSSETUP) PARM('xx')
```

> 💡 **何が起きるか（ネタバレ注意）**:
> このプログラムは `OPSxxA`・`OPSxxB`・`OPSxxC` という 3 つのジョブを投入し、参加者専用のメッセージ待ち行列（`STUDYxx/OPSMSGQ`）を初期化します。ただし、**そのうちいくつかは正常に動いていません**。どれがどう異常なのかを、このあと Bob と一緒に実機上で見つけていきます。

> ⚠️ **承認のポイント**:
> Rules（`.bob/rules/ops-safety.md`）に基づき、Bob は CL コマンド `execute_cl_command` の実行前に内容と影響を説明して承認ボタンを求めます。内容を確認して承認してください。

## ステップ1: サブシステムの一覧を見る（3分）

```
現在のサブシステムの一覧を表示してください。
サブシステム名・ライブラリー・状況・現在のアクティブジョブ数・最大ジョブ数・説明を表にしてください。
アクティブジョブ数が多い順に並べてください。
```

**期待される動作**:
- Bob が `QSYS2.SUBSYSTEM_INFO` を使った SELECT を実行
- `QBATCH`、`QINTER`、`QSYSWRK`、`QUSRWRK`、`HANDSON` などが表示される

### 1.1 自動開始ジョブを確認する

```
サブシステムが起動したときに自動で立ち上がるジョブ（自動開始ジョブ）の一覧を、
サブシステム別に表示してください。
```

> 💡 **運用者視点のポイント**: 「サブシステムを再起動したら上がってくるジョブ」と「手動やスケジューラーで投入しないと上がらないジョブ」を区別しておくことが、LAB3 の停止ジョブ検知の前提知識になります。

## ステップ2: ジョブの稼働状況を見る（4分）

### 2.1 特定サブシステムのジョブ

```
サブシステム HANDSON で動いているジョブの一覧を表示してください。
ジョブ名・ユーザー・ジョブ番号・状況・ジョブタイプ・実行中の機能を表にしてください。
DETAILED_INFO は NONE で軽量に取得してください。
```

**期待される結果（例：STUDY01 の場合）**:

| ジョブ名 | ユーザー | 状況 | 補足 |
|---------|---------|------|------|
| OPS01A | STUDY01 | DLYW | 稼働中 |
| OPS01C | STUDY01 | **MSGW** | **応答待ち ← 要対応** |

> 🤔 **気づきましたか？** ステップ0 で3つ投入したはずなのに、`OPS01B` がいません。これが LAB3 のテーマです。

### 2.2 応答待ち（MSGW）のジョブをシステム全体から探す

```
システム全体で、状況が MSGW（メッセージ応答待ち）のジョブを探してください。
見つかったジョブについて、どのメッセージ待ち行列のどんなメッセージに対して
応答を待っているのかも調べてください。
```

**期待される動作**:
1. `ACTIVE_JOB_INFO` を `JOB_STATUS = 'MSGW'` で絞り込み
2. `QSYS2.MESSAGE_QUEUE_INFO` で**未回答の照会メッセージ**を検索
3. `OPS01C` が `STUDY01/OPSMSGQ` に「前日分の集計データが未確定です。処理を続行しますか？」と問い合わせて止まっていることが分かる

> ⚠️ **ここではまだ応答しません。** LAB3 で、原因を確認してから応答します。

## ステップ3: スケジュールジョブを確認する（2分）

```
ジョブ・スケジュール項目（WRKJOBSCDE で見える内容）を一覧にしてください。
ジョブ名・状況・頻度・スケジュール時刻・次回投入日・実行コマンドを表にし、
状況が保留（HELD）になっているものがあれば強調してください。
```

> 💡 **運用者視点のポイント**: 「スケジュールが保留のままになっていて、夜間バッチが流れていなかった」は実際によくある障害です。保留中の項目を一目で探せることを確認しましょう。

## ステップ4: 稼働状況レポートを作る（5分）

ここまでの実機調査結果を、朝会や引き継ぎでそのまま使える HTML レポートにまとめます。

```
接続先 IBM i の最新の稼働状況を取得し、運用担当者向けの「IBM i 稼働状況レポート」を HTML で作成して docs/稼働状況レポート.html に保存してください。

【レポート構成】
1. ヘッダーサマリー（確認日時、システム名、現在のユーザー名、要対応件数バッジ）
2. 【要対応事項】（MSGW 応答待ちジョブ、未回答の重要メッセージ、保留中スケジュールを赤系アラートで強調）
3. サブシステム稼働状況一覧
4. HANDSON サブシステム内のジョブ詳細一覧
5. スケジュールジョブ一覧（次回実行予定・保留状態）
6. 運用担当者への推奨アクション（次に何をすべきか）

※ 最新状態を反映するため、各 IBM i Services（SQL）を再実行してレポートを生成してください。
```

**期待される動作**:
1. Bob が必要な SQL（`ACTIVE_JOB_INFO`、`MESSAGE_QUEUE_INFO`、`SCHEDULED_JOB_INFO` 等）を実機に対して実行し、最新データを取得します。
2. 取得した実機データを綺麗にスタイリングされた HTML テーブルおよびアラートカードとして構成します。
3. `docs/稼働状況レポート.html` を保存します。

💡 **確認方法**: エクスプローラーで `docs/稼働状況レポート.html` を右クリック →「統合ブラウザーで開く（Simple Browser / Live Server 等）」でプレビューします。

## 💡 このラボで学んだこと

✅ **5250 画面を何枚も開いていた確認作業が、1つの会話で完結する**

| これまで | Bob では |
|---------|---------|
| `WRKSBS` | 「サブシステムの一覧を見せて」→ `SUBSYSTEM_INFO` |
| `WRKACTJOB SBS(xxx)` | 「HANDSON のジョブを見せて」→ `ACTIVE_JOB_INFO` |
| `WRKACTJOB` で MSGW を目視 | 「MSGW のジョブを探して」→ 状況で絞り込み |
| `DSPMSG QSYSOPR` | 「未回答のメッセージは？」→ `MESSAGE_QUEUE_INFO` |
| `WRKJOBSCDE` | 「スケジュールの一覧」→ `SCHEDULED_JOB_INFO` |

✅ **結果を「レポート」として残せる**
- 確認作業の証跡として、そのまま引き継ぎや報告に使える

✅ **ただし「本来いるべきジョブがいない」は、一覧を見るだけでは気づきにくい**
- `OPSxxB` の不在に気づけたのは、ステップ0 で「3つ投入した」と知っていたから
- 実際の運用では「何が動いているべきか」を**定義しておく**必要があります → LAB3 へ
